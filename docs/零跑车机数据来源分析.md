## 0. 先纠正一个前提：`127.0.0.1:5555` 到底指什么

上一版清单里我写了"零跑车机本地 ADB（`127.0.0.1:5555`）是否可用"，这个表述容易被误读，在此更正：

| 项 | 实情 |
|---|---|
| `127.0.0.1:5555` | 是**车机自己**（或模拟器）内的 `adbd` 回环端口。BYD 车机的 `adbd` 常开，所以 BYD 那条线能用它。 |
| **零跑车机** | **没有可用的 adbd**。所以上一版清单里所有"走 ADB"的零跑适配思路**全部作废**。 |
| 本次验证 | 逆向确认 `VehicleSetting` **完全不使用 ADB** —— 全包内 `Runtime.exec` 只用来做本地文件操作（如 `chmod 666 /data/leapmotor/VehicleConfigurationBean`），没有任何 `adb shell` / `app_process` / `su`。 |

**⇒ 结论：零跑适配只能走"车机系统公开的进程间通道"**：广播、AIDL 绑定服务、ContentProvider、文件。下面逐项给出对照。

## 2. 核心通道 A：整车 CAN 广播（★最重要）

### 2.1 请求 / 响应协议（与现有 `LeapmotorGearMonitor` 完全一致）

```
请求:  sendBroadcast(Intent("leapmotor.apptocan.update").putExtra("upgradeAsk", "upgrade"))
响应:  广播 "leapmotor.cantoapp.update"
       每个 CAN 信号 = 一个 Intent extra，key 是**十进制信号码**字符串，value 是 Int 或 Float，
       未取到时默认值 -1（Int）/ -1.0f（Float）
```

证据（`VehicleSetting`）：
- `setting/system/update/UpdateTools.smali:213-222` —— `getCandata()` 注册 `leapmotor.cantoapp.update` 后发 `leapmotor.apptocan.update` + `upgradeAsk=upgrade`
- `setting/system/update/UpdateTools$CanDataReceiver.smali` —— `onReceive` 里逐个 `getIntExtra` / `getFloatExtra`

> 这与我们 `common/LeapmotorGearMonitor.kt` 已实现的完全同一条路（`REQUEST_ACTION` / `RESPONSE_ACTION` 一字不差），
> 说明**该通道已被实车验证可用**，只是我们只用了一个 key。

### 2.2 信号码 → 字段对照表（从 `UpdateTools$CanDataReceiver.smali` 逐行解出）

| 信号码 | 类型 | 字段名（原包变量名） | 含义 | 对应原 BYD 功能 |
|---|---|---|---|---|
| `100001` | Int | `icuSpeed` | ICU 车速 | **速度** |
| `1100412` | Int | `speedEffective` | 有效车速 | **速度** |
| `1100409` | Float | `absEscSpeed` | ABS/ESC 车速 | **速度**（高精度） |
| `1060122` | Float | `batteryVoltage` | 电池电压 | 电池 |
| `1060115` | Int | `batterySOC` | 电池 SOC（电量） | **电量** |
| `1060306` | Int | `batterySOH` | 电池健康度 | 电池 |
| `1030115` | Int | `powerSOC` | 动力电池 SOC | **电量** |
| `1030505` | Int | `fastCharge` | 快充状态 | **充电** |
| `1030506` | Int | `slowCharge` | 慢充状态 | **充电** |
| `1110113` | Int | `epb` | 电子驻车状态 | 驻车/视频门控 |
| `1010105` | Int | `stall` | **档位**（1=R 2=N 3=D 其它=P） | 档位 ✅ 已用 |
| `1060102` | Int | `on1` | 开关量 1 | 待判定 |
| `1060103` | Int | `on2` | 开关量 2 | 待判定 |
| `1060104` | Int | `on3` | 开关量 3 | 待判定 |
| `1020101` | Int | `machine` | 车辆状态机 | 待判定 |

> ⚠️ **单位/缩放尚未确认**。原包只做 `getIntExtra(key, -1)` 直读，没有除以 10 之类的换算，所以**大概率是已换算好的整数**
> （`batterySOC` 很可能直接是 0–100，`icuSpeed` 直��是 km/h）。但**必须实车抓一次日志核对**，
> 特别是 `absEscSpeed`（Float）和 `speedEffective` 哪个更准。

### 2.3 判定"收到有效数据"的规则

原包对每个信号都用 **`-1` / `-1.0f` 作为"未取到"哨兵**。所以：

- `intExtra == -1` ⇒ 该信号**本帧没带**（或确实无效），**不能当 0 用**；
- 收到任意非 -1 值 ⇒ 可采信。

这条与我们 `LeapmotorGearMonitor` 里"收到任何档位数据之前一律返回 null（禁止视频）"的思路一致，应沿用。

### 2.4 轮询节奏

原包在**升级条件检查**场景下用：`delayGetCanDataOnce()`，同一个 condition 连续超过 **12 次**（`checkCanDataTimes > 0xc`）就 `stopReceiveCanData()`。
即"发一次请求、收若干帧、超时放弃"。我们做常驻监控时，建议**1 Hz 主动轮询**（现有 `LeapmotorGearMonitor` 就是 `POLL_MILLIS = 1000`），无需照搬它的 12 次上限。

## 8. 建议的实现方案

### 8.1 先做一件事：把 `LeapmotorGearMonitor` 升级为 `LmVehicleSignals`

现在这个类名叫 GearMonitor，但**通道本身就是整车信号总线**。建议：

1. 重命名为 `LmVehicleSignals`（或保留类名、扩大职责），**一次请求解全部 key**；
2. 暴露强类型快照：
   ```kotlin
   data class LmVehicleSnapshot(
       val gear: Int?,          // 1010105
       val speedKmh: Int?,      // 1100412 / 100001
       val soc: Int?,           // 1060115 / 1030115
       val voltage: Float?,     // 1060122
       val soh: Int?,           // 1060306
       val epb: Int?,           // 1110113
       val fastCharge: Int?,    // 1030505
       val slowCharge: Int?,    // 1030506
   )
   ```
3. `LeapmotorGearMonitor` 变成它的薄封装（保持现有调用点不动）；
4. 各功能订阅快照：视频门控读 `gear`，`batteryToIphone` 读 `soc/voltage`，`wheelSpeedToIphone` 读 `speedKmh`。

**这样一次性补齐 §1～§4 四个 BYD 独有功能，且代码量最小。**

### 8.2 再做胎压：`LmHealthClient`

### 8.3 蓝牙挂起的更正

原清单说"零跑蓝牙挂起要 ADB"——**错了**。`BydBluetoothSuspend` 用 `svc bluetooth` 是因为 BYD 走 ADB；
零跑侧完全可以直接用**普通 Android API**：
```kotlin
BluetoothAdapter.getDefaultAdapter().disable()  // 需要 BLUETOOTH_ADMIN 权限（普通权限）
```
不需要 ADB。这条从"✗"上调为"⚠️ 可行"。
